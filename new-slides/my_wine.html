Décision n°1 : séparer PE 32-bit (PE32) et PE 64-bit (PE32+)

Deux formats proches, mais deux largeurs de pointeurs et deux mécaniques d'exécution.

my_wine

Lit la signature historique MZ, suit e_lfanew, vérifie PE, puis distingue 0x10b et 0x20b.

my_wine64

Processus Linux en architecture x86 64-bit (x64) : convention Microsoft côté guest, System V côté host.

J'ai choisi deux processus natifs plutôt qu'une couche d'émulation de pointeurs : le noyau et le compilateur garantissent directement la bonne largeur d'adresse.

Concept 1 : un PE est une recette d'image mémoire

Comme l'Executable and Linkable Format (ELF), ce n'est pas « du code à lancer » : le format décrit quelle mémoire construire.

Le chemin de lecture utile

Header Disk Operating System (DOS) Ancien header MZ. Son intérêt principal : e_lfanew donne l'offset des vrais headers PE.
Headers PE Signature PE\0\0, machine, point d'entrée, ImageBase, SizeOfImage, data directories.
Section table Sections telles que .text, .rdata, .data, .rsrc, .reloc.

Comparaison utile avec ELF

ELFLes segments PT_LOAD et le bloc dynamique dominent l'histoire.
PELa section table et les data directories deviennent le point d'entrée mental.
ConséquenceOn suit surtout des adresses relatives, des sections et des data directories.
Même méthode que pour ELF : lire la recette sur disque pour reconstruire l'image attendue en mémoire.

Concept 2 : trois coordonnées pour une même adresse

Ces trois mots gouvernent presque toutes les conversions d'adresse du loader.

Distance dans l'image

Relative Virtual Address (RVA)

Distance depuis le début logique de l'image PE. Ce n'est pas un pointeur absolu.

RVA(entry) = 0x1230
ImageBase

Base préférée

Adresse à laquelle le binaire aimerait être chargé si tout se passe idéalement.

ImageBase = 0x00400000
Adresse finale

Virtual Address (VA)

Adresse effective après chargement. C'est elle que le processeur lira.

VA = actual_base + RVA
Le loader passe son temps à transformer des RVA en vrais pointeurs C. Toute erreur ici se propage ensuite dans les imports, les ressources, les relocations et le point d'entrée.

Concept 3 : reloger si la base préférée est occupée

Si l'image n'est pas chargée à son ImageBase, les adresses absolues internes deviennent fausses.

effet

corriger la valeur pointée, pas déplacer la section
delta = actual_base − ImageBase : on corrige les pointeurs, pas la position logique des sections.

D'abord : qu'est-ce qu'un registre du processeur ?

Une instruction travaille d'abord avec quelques cases nommées, situées dans le processeur. La mémoire vive contient le reste.

Dans le processeur · accès immédiat

Registres générauxRAX, RCX… transportent nombres, adresses et arguments.
Registre de pileRSP en 64-bit ou ESP en 32-bit désigne le sommet de la pile active.
Registres de segmentFS et GS conservent une base implicite vers une zone mémoire particulière.
⇄

Dans la mémoire vive · beaucoup plus vaste

code et données

état du thread et du processus
Un registre n'est pas une variable magique : c'est une petite case matérielle à laquelle l'architecture donne un rôle. FS et GS servent ici à fabriquer une adresse mémoire.

FS et GS ne découpent pas ici toute la mémoire : ils offrent un raccourci matériel vers le contexte Windows courant. Le bridge doit restaurer le contexte Linux avant d'appeler du code host.

Une pile guest n'est pas un simple buffer : c'est le premier état observable par le code appelé.

Le même opcode syscall, pas le même noyau

Dans la famille Windows New Technology (NT), numéro, arguments, handles et code de statut NT (NTSTATUS) forment un contrat indivisible.

Appel Windows NT

numéro + arguments Microsoft + objets Windows

Chemin incorrect

Instruction envoyée à Linux

Mauvaise table de numéros, mauvaise lecture des arguments, résultat Linux sans sémantique Windows.

Chemin correct

Intercepter → décoder → traduire

Le bridge appelle un handler host, puis reconstruit un handle ou un NTSTATUS Windows.

Le même opcode ne désigne pas le même service : sans bridge, on entre dans le mauvais noyau avec le mauvais numéro.

Convention d'appel C 32-bit (cdecl)

Tous les arguments sont relus sur la pile, après les frames ajoutées par le thunk et le dispatcher.

Convertir la pile ne veut pas dire la recopier : on sauve son adresse, on bascule vers une pile host, puis on sait décoder les bons offsets.

Limite actuelle

Le chemin n'injecte pas encore toutes les fautes comme exceptions Windows récupérables.

Aujourd'hui, ce chemin rend les crashs observables et survivables côté host ; ce n'est pas encore une traduction complète de tous les signaux en exceptions Windows récupérables.

Comme dans ld.so : savoir quand la bibliothèque C est interdite

Le changement de pile et de registre de segment découpe le programme en zones de sécurité différentes.

Avant le handoff

zone host

Parsing, configuration et allocation peuvent utiliser normalement la bibliothèque C standard (libc) Linux.

→
Après le handoff

zone sensible

Helpers sans libc, syscalls bruts et état explicitement contrôlé.

→
Appel natif nécessaire

bridge explicite

Restaurer le contexte host, appeler Simple DirectMedia Layer 2 (SDL2) ou la libc, puis remettre le contexte guest.

C'est le même piège que dans ld.so avant l'initialisation de libc, mais il réapparaît ici à chaque traversée guest → host.

Doom95 : une preuve d'intégration, pas le cœur du talk

Le jeu vérifie que les ponts fonctionnent ensemble. Le temps d'implémentation vient surtout de la largeur de l'interface de programmation applicative (API) et du boilerplate.

Une vraie frame de Doom95 produite par le runtime.
Les mécanismes réutilisables

Image PE, IAT, TEB/PEB, pile guest, conversion d'ABI, signaux et passages explicites vers le host.

Ce qui a surtout coûté du temps

Dialogues, ressources, DirectDraw, DirectSound, Windows Multimedia (WinMM) et multiplication des stubs Win32.

Doom donne une preuve d'intégration spectaculaire ; la valeur technique durable est dans les mécanismes qui rendent cette intégration possible.
