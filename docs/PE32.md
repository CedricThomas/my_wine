**Goal**: Execute 32-bit PE code inside the 64-bit `my_wine` process by switching to 32-bit compat mode via `ljmp`.

**What was built**:

9. Fixup_far32 far pointer struct for 32-bit return path (`4fa3116`)
10. Crash at ret32 tramp in **64-bit mode** — 64-bit code hitting the 32-bit entry tramp (`355d612`)
11. Added int3 breakpoint, CS dump, fault address diagnostics (`50dad39`, `f8af5e7`, `1669994`)
12. Restructured blob layout, fixed thunk EDI, fixed return path — still crashing (`c69af67`)
13. `fs_intercept` module for SIGSEGV-based fs:[offset] interception (`43e161b`)
14. TEB GdiTebOffset fix for PE32 CRT bootstrap (`378f672`)

The crash at the ret32 tramp kept recurring because 64-bit code was somehow jumping to the 32-bit entry tramp.

**Pivot**: `3e3349d` — `revert: remove 64->32 mode-switch approach, prepare for 32-bit ELF helper`

### Resolved: FS→TEB Setup (Phase 5-6)

The 32-bit standalone binary (`my_wine_32`) uses `-nostartfiles -Wl,--no-dynamic-linker`.
`arch_prctl(ARCH_SET_FS)` returns `EINVAL` (`errno=22`) for 32-bit processes on a 64-bit kernel.
The kernel explicitly rejects this syscall in compat mode — it only works for native 64-bit processes.

**Fix applied (Phase 5-6)**: Replaced `INLINE_SYSCALL_ARCH_PRCTL(ARCH_SET_FS, teb)` with `set_thread_area` (syscall 243 via `int $0x80`).
This creates an LDT entry pointing to the TEB, then loads the returned selector into `%fs`.

### WoW64 Migration Assessment

The dual-process approach (fork+exec `my_wine_32`) works but adds complexity:
separate build, separate entry, separate signal handling. Wine uses in-process WoW64
mode-switching instead, which would simplify the architecture long-term.

**Wine's WoW64 approach**:
1. **GDT setup** — Create 32-bit CS/DS selectors via `modify_ldt`
2. **Mode switching** — `ljmp`/`lcall` between 64-bit and 32-bit code segments
3. **Dual stack** — Switch to 32-bit TEB stack before executing 32-bit code
4. **FS via LDT** — `set_thread_area` (syscall 243) creates LDT entry → `mov sel, %fs`
5. **Signal handling** — 64-bit signal handler that switches to 32-bit mode before returning

**Why Phase 2 failed but Wine works**:

| Aspect | Phase 2 (failed) | Wine (works) |
|--------|------------------|-------------|
| GDT setup | Ad-hoc selectors via inline asm | `modify_ldt` with proper 16-byte struct, full segrights |
| Mode switch | `ljmp` at CPL=3 (kernel blocks) | `lcall` with proper CS type/dpl bits; or pure 32-bit child process |
| Stack switching | Single stack, crashes on mode change | Dual stacks: switches to 32-bit TEB stack before `int $0x80` |
| FS setup | `arch_prctl` (doesn't work in 32-bit) | `set_thread_area` (syscall 243) → LDT entry → `mov sel, %fs` |
| Signal handling | Not implemented | `SA_SIGINFO` handler with mode-aware ucontext |

**Migration scope**:
- **5 new files** (~370 lines): `woW64_entry.S` (mode-switch trampolines), `woW64_gdt.c` (LDT/FS setup), `woW64_signal.c` (mode-aware signal handler), `wow64.h` (API), `dispatcher_entry_32.h`
- **3 major rewrites**: `main.c` (remove fork+exec), `dispatcher_entry_asm.S` (add 32-bit mode-switch entry), `pe32_entry.c` (standalone → module)
- **5 moderate changes**: `crash_handlers.c`, `teb_peb.c`, `thunk_gen.c`, `syscalls_inline.h`, `Makefile`
- **5 minimal changes**: `dispatcher.c`, `image_mapper.c`, `dispatcher_entry.c`, `entry.c`, `pe32_entry.S` (remove)
- **Total**: ~8-10 days focused implementation

**Recommended migration path**:
- **Phase 1** (highest risk): GDT + mode switching infrastructure, `set_thread_area` for FS
- **Phase 2**: Dispatcher + thunk integration, build system
- **Phase 3**: Signal handling + cleanup

**Dual-process remains viable** — the fork+exec approach is simpler to implement and debug.
The WoW64 migration is a future optimization, not a prerequisite for running PE32 binaries.

## Lessons Learned

1. **Mode-switching is a dead end** — kernel enforces CPL=3 restrictions. Dual-process was the right architecture.
2. **Checkpoint every change** — every commit is preceded by a checkpoint. Enables instant bisection.
3. **32-bit inline asm is fragile** — INLINE_SYSCALL_MMAP broke because the macro assumed 64-bit registers. Use synct_mmap2() assembly wrapper instead.
4. **CRT bootstrap is the hard wall** — loader infrastructure can be built, but each CRT variant (Watcom, MinGW, MSVC) has unique requirements.
5. **Static 32-bit = no TLS** — when using -nostartfiles -Wl,--no-dynamic-linker, musl TLS is never initialized. GS stays 0x0. Every libc function that internally uses syscall() (via call *%gs:0x10) will crash. All code in the 32-bit child must use INLINE_SYSCALL_* macros or raw int $0x80 inline asm. No bare mmap(), sigaction(), perror(), or any other libc call.
6. **GDB misattributes crash sites in 32-bit static binaries** — the SIGSEGV in __libc_do_syscall was reported at setup_unix_stack() because GDB scans the stack for return addresses and finds the nearest frame. The actual crash was in generate_all_thunks() → libc mmap. Always verify with objdump disassembly.
7. **`arch_prctl(ARCH_SET_FS)` doesn't work in 32-bit mode on 64-bit kernel** — returns `EINVAL`. The kernel explicitly rejects it in compat mode. Use `set_thread_area` (syscall 243) instead to create an LDT entry, then load the returned selector into `%fs`. This is how Wine handles it.
8. **Phase 2 didn't fail because mode-switching is impossible** — it failed because of GDT setup details (segrights, selector format) and lack of dual-stack switching. Wine's WoW64 approach works by combining proper `modify_ldt` setup with stack-switching trampolines. The 30 commits of Phase 2 were close — the final fix was `ljmp` → `lcall`, but without the proper GDT entries and dual stacks, it couldn't get past the kernel checks.
9. **Data vs function imports matter** — MinGW CRT imports `__p__acmdln`/`__p__fmode`/`__p__commode` via JMP thunks (calling them as functions), not as data reads. Resolving them to data addresses in the IAT caused SIGSEGV when the thunk jumped to data. Wrapper functions returning the pointer value fixed it.
10. **pthread_mutex uses TLS** — even simple heap locking via `pthread_mutex_t` crashes in `-nostartfiles` 32-bit builds because musl's `pthread_mutex` internally accesses `gs:[0x10]`. Guard with `#ifndef MY_WINE_32`.
